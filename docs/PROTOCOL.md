# Protocol version 1

## Ownership and evaluation layers

The library defines contracts, validates packs/profiles, supervises bounded execution and writes evidence. Consumers supply domain scenarios, registered runners, trusted graders and approval policies. NERV is one consumer; no NERV source import, deployment or acceptance gates a Gauntlet release.

`system` evaluates deterministic system behavior. `model` evaluates judgment or structured answers. `coding` evaluates coding-agent tasks through a registered runner. `end-to-end` evaluates complete scenarios through a registered runner. Reports keep these layers distinct; system passes cannot qualify model capabilities. No opaque overall intelligence score is generated.

The direct local provider supports Ollama's loopback API, exact installed quantization/digest checks, explicit context/output/sampling/thinking requests and independent text/JSON equality grading. Endpoint registration is trusted: a loopback URL is not proof that an administrator has not configured a proxy. Remote-backed Ollama model metadata is rejected. Generic API compatibility is not a claim that every runtime parameter is independently observable.

## Inputs and execution

Pack: `schemaVersion`, `id`, semantic `version`, `cases`. Each case has stable `id`, `layer`, `split` (regression or holdout), named `capabilities`, `critical`, `expensive`; either `runner`, or model `messages` plus independent `expected: {kind: "text"|"json"|"rubric"|"defects", value}` ([rubric grading](#rubric-grading), [defect-finding grading](#defect-finding-grading)). No shell commands in packs. Expectations are never sent to the direct model.

Model profiles can declare `weightsBytes` and `minimumMemoryBytes` together, alongside their quantization and context. Machine environments declare total memory and an owner-reviewed accelerator class. Planning with both declarations reports host fit, makes every case ineligible on a memory misfit and leaves missing sizing explicitly unknown; execution enforces the same memory gate before contacting a provider.

Ordered model messages may represent a complete prior transcript, including assistant content followed by a correcting user message. The array is validated, fixture-hashed and forwarded unchanged for one final generation; Gauntlet does not generate intermediate turns or execute an interactive dialogue. The [expanded-pack contract](EXPANDED-PACK.md) records the coverage matrix, versioning and holdout limits.

Profile: exact model tag/quantization, loopback endpoint, context, maximum output, nullable temperature/topP/topK/seed/think, concurrency, hardware and cache description. Null sampling settings inherit runtime defaults, so runtime version/default changes require reevaluation. Candidate profiles are configuration proposals, not qualification. The baseline executor is serial; a profile requesting parallel execution fails closed until a suitable scheduling adapter is supplied.

Limits: per-case milliseconds, whole-suite milliseconds, maximum selected cases, repeats, aggregate output-token ceiling and per-response/log bytes. Each direct call reserves its maximum output before execution; unmeasured or over-budget model execution stops later model calls. Timeouts cancel HTTP requests or kill external process groups. A client cancellation cannot independently prove an uncooperative server stopped compute. SIGINT/SIGTERM cancels the active request or owned process group and marks later cases not-run. Signal handlers are removed when the suite finishes. SIGKILL, abrupt machine loss or a separately detached descendant cannot be cleaned up by JavaScript; deployment supervisors and adapter contracts own those limits. No automatic retries. Truncation is an error; skipped or omitted work is not a pass. Separate expensive/model opt-ins are required, in addition to explicit execution.

Legacy/default calls unload after each response (`keep_alive: 0`); suite-resident profiles keep warm state between cases. See [performance measurement](PERFORMANCE.md). Durations therefore include cold-loading effects and are not steady-state throughput measurements. Provider input tokens and sampled memory/device counters are retained when telemetry is enabled. Energy and human repair/review time are not measured; do not report them as zero or infer them from output tokens. No server-wide configuration is changed.

## Registered external runners

A separately reviewed registry has `schemaVersion: 1` and a `runners` object. Entries have fixed `command`, `args`, `cwd`, accepted `layers` and `allowModels`. Relative cwd resolves from the registry's directory. There is no shell interpolation; supported argument placeholders are `{report}`, `{profile}` (ID), `{configuration}` (private JSON profile path), `{budget}` (private remaining-budget JSON path), and `{case}` (private current-case JSON path). Model/agent adapters must receive configuration, current case and remaining budget. Owner-trusted adapters enforce token limits before starting their work; the protocol verifies reported usage afterward and stops subsequent work on missing/excess usage.

Processes receive PATH, HOME and TMPDIR only. Model credentials are not inherited. Commands are **trusted executable code**, not candidate-controlled input. POSIX process-group supervision bounds runtime/output and cleans descendants; it is not a security sandbox. Windows external execution is unavailable until a Job Object adapter is implemented. Direct local-provider and schema operations remain portable.

Coding runners must supply an independently enforced sandbox/worktree, candidate/test separation and trusted acceptance tests. This release provides the bridge, not a built-in coding sandbox or Inspect installation. Inspect AI and other established runners can normalize their results into this contract; compatibility is not claimed until a particular adapter is implemented and tested.

The adapter writes a new report at `{report}`:

```json
{"schemaVersion":1,"layer":"system","sourceStable":true,"complete":true,"results":[{"id":"policy","status":"passed","checks":3}]}
```

Statuses: passed, failed, error, not-run. Empty/zero-check/incomplete evidence cannot pass. Non-system reports also need `configurationHash` (SHA256 of `JSON.stringify(profile)`), `modelDigest` measured `outputTokens`, `runtimeIdentity`, `caseHash` (hash of the current case), and `fixtureHash` (the independently evaluated input/fixture identity). Distinct case IDs or regression/holdout labels do not create independent coverage when fixture hashes repeat. A holdout fingerprint also used for regression does not count as heldout. A nonzero runner exit is an error even if its output claims success. Evidence hashes identify bytes/configuration; they are not cryptographic attestations of truthful measurement or authenticated authorship. The registered runner/grader remains part of the trusted computing base.

## Evidence and qualification

Reports include pack/profile/registry hashes, declared case count, model digest, runtime identity, selection results, iterations, layer/capability tags, timing, response or adapter hashes, token measurements, complete/pass/source-stability flags and `promotion: false`. Source/profile mutation invalidates acceptance. Responses/prompts and raw process logs are not copied into reports. Existing evidence is never overwritten.

A pending-only run preserves the full pack hash and result shape. Cases proven current by the supplied ledger are `not-run` with reason `skipped-current`; this one explicit reason is neutral for report completeness and pass/fail calculation. Other skipped, unauthorized, cancelled or omitted work remains incomplete and cannot pass. Pending-only execution bypasses automatic full-report cache reuse so every case classified pending is actually executed. See [run ledger and pending cases](LEDGER.md).

Execution atomically checkpoints the private output report after each case. A resumed campaign admits only graded results from a matching checkpoint; interrupted errors and unrun cases execute again. Source, full pack and case metadata, evaluator/protocol, limits, registry, profile, scenario and available runtime/model identity must match before any result is carried forward. Resume writes a new report and does not weaken model, cost or scenario admission. See [evidence checkpoints and reuse](EVIDENCE.md).

`compare --reports=a.json,b.json` preserves errors/not-run counts and unknown usage. Different pack/registry/budget contracts are marked noncomparable. Configuration changes remain visible; comparison alone chooses no winner. The [repeatable comparison contract](COMPARISONS.md) defines the bounded candidate matrix, identity fields, compatibility dimensions and repetition limits.

`qualify --report=report.json --review=receipt.json --requirements=examples/requirements.json --out=results/reviewed-profile.json` exports a harness-compatible profile only when stable complete model evidence meets each capability's minimum unique cases, minimum unique holdouts and pass rate, with all critical cases passed and known usage. Repeats do not inflate unique-case coverage. Capability minima are owner-authored and task-specific; meeting a small smoke threshold does not establish broader fitness.

A receipt has `schemaVersion: 1`, `reportHash`, nonempty `reviewer`, `accepted: true`, reviewed `capabilities`, ISO `reviewed` timestamp after report completion, and a nonempty `evidence` reference. It is an explicit owner attestation, not an authenticated independent identity. A qualified export is reviewable data; it never edits a consumer's profile registry, changes permissions, runs a task or approves a production promotion.

## Improvement cycle

Capture a failure, add a regression and separately maintained holdout, prepare an isolated candidate configuration, compare under the same acceptance contract, independently review, then let the consumer's existing owner process decide promotion. Preserve the prior configuration and rollback/monitoring evidence. This supports measured self-improvement without automatic weight training, evaluator rewriting or self-granted permissions.

## Ollama response formats

Direct model cases may set `responseFormat` to `"json"` or a JSON object schema (`type: "object"`, at most16KiB). Omit it for unconstrained generation. Reference/resolution keywords are rejected; schemas are passed to local Ollama, never fetched. The schema's semantic validity is ultimately checked by Ollama; invalid provider requests remain errors. This release does not implement a general JSON Schema validator. JSON grading is required; runner cases cannot set this field. Other runtime backends reject it before provider work instead of silently dropping it.

The adapter forwards this field as `/api/chat`'s `format` for streaming and non-streaming requests. Planning labels unconstrained/json/schema. Pack hashes include the exact format, separating cache/report identity. Prompt fixture hashes remain prompt-based so format changes cannot manufacture independent holdout coverage. Expected answers are never sent by the grader. Schemas are public test inputs: do not encode the expected answer through const/enum or other semantic constraints unless that is explicitly the task being evaluated.

`examples/smoke-schema-v1.json` is a separate ten-case structural variant of `smoke-v1.json`; only keys/types/required/additionalProperties are constrained. It preserves prompts and independent expected answers. Valid JSON can still be wrong: exact semantic grading and private failed-final capture remain unchanged. Historical unconstrained reports are not reclassified. Across modes, compare observations with configuration differences explicit; automatic equivalence is false.

Ollama documents `format: "json"` and JSON schemas at https://docs.ollama.com/capabilities/structured-outputs. Native local Ollama is the supported boundary here; no cloud claim follows.

## Coding isolation and holdout limits

Gauntlet provides an external-runner contract, not coding isolation. A worktree separates files for coordination; it does not enforce access restrictions. The selected runner must implement an independently enforced execution boundary, protected workspaces, candidate/test separation and trusted grading outside candidate control. Process supervision, hashes and owner registration do not supply those safeguards.

Holdout integrity is procedural in the protocol itself. Separate maintenance, fixture identities and configuration hashes identify declared inputs and prevent duplicate coverage from being counted as independent; they cannot prove that an agent never read hidden tests, expected answers or grader code. Claims of inaccessible holdouts require runner-specific evidence of an enforced boundary, including denied filesystem/network/tool access and a grader outside the agent's authority. The coding-v1 reference runner below supplies an enforced execution boundary and an out-of-process grader for its own tasks, with contract tests; its holdouts are public and therefore exposed. Other runners remain unverified until they show the same evidence. A successful contract fixture or qualification export does not establish either property.

## Coding pack grader

`examples/coding-v1.json` declares coding-layer cases on the `coding-reference` runner. Each task in `examples/coding-v1/tasks/<case>/` has a prompt and starter file (what the candidate sees), the function to call and `cases.json`: inputs with the return value or error each must produce. Grading is out of process. The candidate's process receives only the candidate, a small driver and the inputs: no expected values, assertions or test framework. The driver calls the function on each input and prints what came back, or the error raised, as the last `GAUNTLET-RESULTS` line of its stdout. `examples/coding-v1/grade.mjs`, outside that process, takes that line from the stdout the executor returns, under a strict schema and a 1 MB cap (a missing, oversized or malformed line fails), and compares it with the expectations only it holds. A case passes only when every input matches. What is graded is the JSON-serialised output of the candidate's process for these inputs: a return value compared by deep equality, or an exception kind compared by the class names the process itself reports (type identity is not checked, so a candidate can name any error kind it likes). Tampering inside the candidate's process (patching a framework, replacing assertions, printing a summary, exiting early) changes only the candidate's own answers. The grader awaits the executor's optional `prepare` (engine check, image pull) before the case's time starts, bounds its own wait (`timeoutMs`) whether or not the executor does and reports a timeout at once, removing the workspace only when the executor resolves, so a process still writing there never delays the verdict; the executor must still stop every candidate process before it resolves, or a leftover process keeps the workspace (`removeLeftoverWorkspaces()` retries). Cleanup unlocks folders a candidate made unreadable, without following links. Fixture identity is the hash of the prompt, starter and cases.

Both parts are required. The executor's enforced boundary ([coding isolation and holdout limits](#coding-isolation-and-holdout-limits)) protects the host and hides the grader's files from the candidate; out-of-process comparison keeps the verdict outside the candidate's reach. The grader runs nothing itself; the repository's tests use a process-group executor on committed trusted candidates only.

`examples/coding-v1/runner.mjs` is the reference runner for these cases (`node examples/coding-v1/runner.mjs {report} {configuration} {budget} {case}`, coding layer, models allowed). It sends the task's prompt and starter, never its cases, to the profile's loopback Ollama model with the profile's sampling settings and the remaining output budget, takes the first fenced code block as the candidate and grades it with `container-executor.mjs`. That executor runs each command in a new container from a pinned image (`python:3.12-alpine`, `node:24-alpine`, by digest) with no network, a read-only root and a small no-exec `/tmp` (16 MB), all capabilities dropped, no privilege gain, the host's non-root user, 256 MB memory without swap, 64 processes, one CPU, a kernel CPU-time limit equal to the case limit (`--ulimit cpu`) and no engine log (`--log-driver none`). Only the grader's temporary workspace is mounted, read-only, at `/work`; the repository, the tasks and the grader are not, and nothing the candidate writes reaches the host. Stdout is capped at 2 MB. Three layers stop a container: an init process with `timeout -s KILL` inside the container, so it dies at the case limit even if the runner is killed; the host-side timer, which removes it, with every call resolving only after its container is gone (SIGTERM and SIGINT to the runner remove its containers too); and, before every case, a sweep that removes labelled containers whose recorded deadline has passed. Images are checked and pulled before the case's time starts. Without a reachable engine it refuses and never runs code on the host. The runner calls only a literal loopback address (`127.0.0.1` or `[::1]`), refuses redirects and uses no proxy. Contract tests check the denied network, the read-only root and workspace, the invisible repository, the non-root user, the timeout and memory kills, a SIGKILLed runner's container stopping by itself, the sweep, pulls outside the case timer, the run flags and the refusal; in CI they are required.

What stays unverified: the container engine and kernel are trusted, so a container escape is outside this boundary; CPU time is capped by the wait, not by an accounting limit; the in-container `timeout` runs as the candidate's user, so a candidate that kills it and then sleeps outlives the case, using no CPU and at most 256 MB, until the runner's timer or the next sweep removes it (a busy loop is still stopped by the CPU-time limit); the model's reply is trusted only as candidate source.

The tasks, expected values and reference solutions are committed to a public repository, so a model may have seen them: the `holdout` cases of this pack are contamination-exposed examples of the split, not unseen holdouts.

## Embedded sketch grader

`examples/embedded-v1/grade.mjs` grades Arduino and ESP32 sketches by compiling them; nothing is uploaded or run. Each task in `examples/embedded-v1/tasks/<case>/` has a prompt and `starter.ino` (what the candidate sees), a board (`fqbn`), regular-expression checks the sketch must match (`requires`) or must not match (`forbids`), and string literals it must contain (`literals`). `examples/embedded-v1/toolchain.json` pins the cores (`arduino:avr` 1.8.6, `esp32:esp32` 3.0.7). The grader writes the candidate alone into a fresh sketch folder, so it supplies no build files or flags; it refuses quoted, absolute, parent-relative or macro includes and file-embedding assembler directives before compiling (`unsafe-include`); it runs the checks on the source with comments and string contents removed, so a requirement named only in a comment or string does not count; and it compiles with `arduino-cli compile --fqbn <board>`, bounding the time (`timeoutMs`, default 300 s) and killing the compiler's process group on timeout. A case passes only when every check and the compile pass; the result names each failed check and keeps the last 4 KB of compiler output with the workspace path removed. The tool is `GAUNTLET_ARDUINO_CLI`, else `/opt/homebrew/bin/arduino-cli` or `/usr/local/bin/arduino-cli`, else `arduino-cli` on PATH. A missing tool, a missing core or a core at another version than the pin is an `error` naming the fix ([setup](guides/arduino-cli.md)), never a failed candidate. Fixture identity is the hash of the task, starter and pins. Contract tests run the grader against a stand-in `arduino-cli` everywhere, and compile every reference and wrong fixture with the real toolchain where it is installed. Real compiles stay out of CI (owner decision 2026-11-25: the ESP32 core download is too large per run); they run on the owner's Mac.

## Raspberry Pi static grader

`examples/embedded-v1/pi-grade.mjs` grades Raspberry Pi Python tasks without running them. Each task in `examples/embedded-v1/pi-tasks/<case>/` has a prompt and `starter.py`, and checks on what the solution must or must not contain: an import, a call by resolved name (`RPi.GPIO.setup`, `gpiozero.LED`; `?.blink` for a method on any object) with literal arguments by position or keyword (pins, modes such as `RPi.GPIO.BCM`, timings), an attribute assignment or read (`?.when_pressed`, `?.is_pressed`), a call inside a `finally` block, and optionally no `while` loop that never blocks (no sleep, pause, wait or await in it). `examples/embedded-v1/pi_facts.py`, run as `python3 -I -B`, byte-compiles and parses the candidate and prints these facts as JSON; it never imports the candidate, so nothing in it runs. A syntax error fails the case (`syntax-error`); otherwise the case passes only when every check passes, and the result names each failed check. Python is `GAUNTLET_PYTHON`, else `python3` on PATH; a missing interpreter is an `error`, never a failed candidate. Fixture identity is the hash of the task and starter.

## Embedded pack runner

`examples/embedded-v1.json` declares eight coding-layer cases in the core area `embedded` on the `embedded-reference` runner: four Arduino and ESP32 sketches (requirement `arduino-cli`, marked expensive because they compile against the pinned cores) and four Raspberry Pi Python solutions (requirement `python3`), each group with regression and holdout cases. `examples/embedded-v1/runner.mjs` (`node examples/embedded-v1/runner.mjs {report} {configuration} {budget} {case} [--arduino-cli=PATH] [--python=PATH]`, coding layer, models allowed) sends the task's prompt and starter, never its checks, to the profile's loopback Ollama model through the same request code as the coding runner (`examples/coding-v1/ollama-candidate.mjs`), takes the first fenced code block and grades it with the sketch grader or the Raspberry Pi grader above. Registered runners receive no extra environment, so tool paths are fixed registry arguments; without them the sketch grader looks in the Homebrew locations and then PATH. For a sketch case it checks the toolchain before asking the model, and a missing tool or core gives an `error` result with the fix on stderr. Nothing is uploaded, imported or run. The contract test runs the whole pack through this runner against a stand-in model and a stand-in `arduino-cli`.

## Rubric grading

`expected: {kind: "rubric", value}` grades free text deterministically, for tasks where no single exact answer exists (catalog grader `rubric-v1`). The value holds at least one of these checks, and the case passes only when all hold:

- `language: "it"` — among the common Italian and English function words in the reply, at least three are counted and at least 80 % are Italian;
- `minWords`, `maxWords` — bounds on the number of words (runs of letters or digits);
- `required` — groups of terms; each group needs one of its terms as whole words, in order for a multi-word term;
- `forbidden` — terms that must not appear as whole words;
- `register: "formal"` — no informal second-person forms (`tu`, `ti`, `tuo`, `puoi` and the like); `"informal"` — at least one.

Matching is case-insensitive on Unicode-normalised text. A failed case's reason names the failed checks (`language`, `min-words`, `required:2`, `forbidden:<term>`, `register`) and never the reply. The word lists are fixed in `src/rubric.ts`, which is part of the engine identity. A rubric measures these observable properties only; it does not judge accuracy or style beyond them, so packs pair it with references reviewed by people.

## Defect-finding grading

`expected: {kind: "defects", value}` grades structured code-review findings deterministically against seeded defects (catalog grader `defects-v1`). The expectation value has:

- `defects` — a non-empty array of seeded defects `{id?, file, lines: [start, end], category}` where `file` is a normalised relative path, `lines` is an inclusive 1-based range and `category` is a lower-case identifier;
- `maxFalsePositives` — optional integer (default `0`), the maximum number of candidate findings that do not match any seeded defect.

The candidate reply must be JSON of the form `{"findings": [{"file": "...", "line": N | "lines": [start, end], "category": "..."}, ...]}` (cases may set `responseFormat: "json"` or an object schema). A finding matches a seeded defect when their normalised relative `file` paths are equal, their lower-case `category` values are equal and their line intervals overlap (`max(findingStart, defectStart) <= min(findingEnd, defectEnd)`); a finding covers at most 10 lines, and a wider one matches no defect and counts as a false positive, so sweeping a whole file cannot find every defect in it. A case passes only when every seeded defect is matched by at least one finding and the count of findings that match no seeded defect is at most `maxFalsePositives`. A failed case's reason names only the missed defect IDs or 1-based indices and the false-positive bound (`malformed-findings`, `missed:<id>`, `false-positives:<count>><max>`) and never copies candidate finding text into the report. `src/defects.ts` is part of the engine identity.
